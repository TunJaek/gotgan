# 국세청 사업자 상태조회 API

곳간이 사업자등록번호로 **계속사업자 / 휴업 / 폐업 / 미등록**을 확인할 때 쓰는 외부 API다.
가입할 때 한 번, 관리자가 존속 점검 명령을 돌릴 때 부른다.

> 이 문서의 요청·응답 예시는 2026-09-28에 실제로 호출해서 받은 값이다(키만 가렸다).
> 폐업·휴업 예시만 실제 번호가 없어 공식 명세(Swagger)를 따랐다.

---

## 1. 한눈에 보기

| 항목 | 값 |
|---|---|
| 제공 | 공공데이터포털 「국세청_사업자등록정보 진위확인 및 상태조회 서비스」 (v1.1.0) |
| 주소 | `POST https://api.odcloud.kr/api/nts-businessman/v1/status` |
| 인증 | 주소 뒤 `?serviceKey=서비스키` (쿼리스트링) |
| 보내는 것 | JSON 본문 `{"b_no": ["사업자번호", ...]}` |
| 한 번에 | 최대 **100개** |
| 받는 것 | JSON (기본값. `returnType=XML`을 붙이면 XML) |
| 명세 | https://infuser.odcloud.kr/api/stages/28493/api-docs |

같은 서비스에 **진위확인(`/validate`)**도 있는데 곳간은 쓰지 않는다. 진위확인은 사업자번호 + 개업일자 + 대표자명을 모두 넣어 "등록증 내용이 맞는지"를 보는 것이고, 곳간이 알고 싶은 "지금 영업 중인지"는 **상태조회(`/status`)**다.

## 2. 요청(Request)

### 모양

```
POST https://api.odcloud.kr/api/nts-businessman/v1/status?serviceKey={서비스키}
Content-Type: application/json

{"b_no":["1088612463","1048145271"]}
```

| 위치 | 이름 | 필수 | 설명 |
|---|---|---|---|
| 쿼리스트링 | `serviceKey` | ✅ | 공공데이터포털 → 마이페이지 → 활용신청 상세의 **'일반 인증키'** |
| 쿼리스트링 | `returnType` | | `JSON`(기본) 또는 `XML` |
| 본문(JSON) | `b_no` | ✅ | 사업자등록번호 **배열**. 1~100개 |

### 꼭 지킬 것

1. **`GET`이 아니라 `POST`다.** 브라우저 주소창으로는 호출할 수 없다.
2. **사업자번호는 숫자 10자리만.** 하이픈(`-`)을 넣으면 오류가 아니라 **"등록되지 않은 번호"로 대답한다**(4-3 참고). 영업 중인 사업자를 미등록으로 잘못 판정하게 된다.
3. **`b_no`는 1개여도 배열이다.** `"b_no": "1088612463"`가 아니라 `"b_no": ["1088612463"]`.
4. **서비스키는 본문이 아니라 주소에** 붙는다.

### 서비스키 형태

포털 화면에는 키가 한 줄뿐이고, `%2F`·`%3D` 같은 글자가 섞인 **주소용으로 이미 변환된 형태**다.

| 쓰는 곳 | 넣는 법 |
|---|---|
| curl·브라우저처럼 주소에 직접 붙일 때 | 포털 키를 **그대로** 붙인다 |
| 곳간 코드(`BiznoStatus`) | `.env`의 `BIZNO_API_KEY`에 포털 키를 그대로 넣는다. 코드가 한 번 풀었다가(`urldecode`) 보낼 때 다시 변환한다 |

변환된 키를 한 번 더 변환해서 보내면 `401 등록되지 않은 인증키 입니다`가 온다(5장 참고). 처음 연동할 때 이 오류가 났던 이유가 이것이다.

## 3. 응답(Response) — 정상

### 실제 응답 (2건 조회: 계속사업자 1 + 미등록 1)

```
HTTP 200
```
```json
{
    "request_cnt": 2,
    "match_cnt": 1,
    "status_code": "OK",
    "data": [
        {
            "b_no": "1088612463",
            "b_stt": "계속사업자",
            "b_stt_cd": "01",
            "tax_type": "부가가치세 일반과세자",
            "tax_type_cd": "01",
            "end_dt": "",
            "utcc_yn": "N",
            "tax_type_change_dt": "",
            "invoice_apply_dt": "",
            "rbf_tax_type": "해당없음",
            "rbf_tax_type_cd": "99"
        },
        {
            "b_no": "1048145271",
            "b_stt": "",
            "b_stt_cd": "",
            "tax_type": "국세청에 등록되지 않은 사업자등록번호입니다.",
            "tax_type_cd": "",
            "end_dt": "",
            "utcc_yn": "",
            "tax_type_change_dt": "",
            "invoice_apply_dt": "",
            "rbf_tax_type": "",
            "rbf_tax_type_cd": ""
        }
    ]
}
```

### 바깥 항목

| 이름 | 뜻 | 비고 |
|---|---|---|
| `status_code` | 호출 결과 | 정상이면 `"OK"` |
| `request_cnt` | 보낸 번호 개수 | |
| `match_cnt` | 국세청에 **등록된** 번호 개수 | 등록된 번호가 하나도 없으면 **이 항목 자체가 빠진다**(4-3 참고). 있다고 가정하고 읽으면 안 된다 |
| `data` | 번호별 결과 배열 | **보낸 순서대로** 온다. 미등록 번호도 한 칸을 차지한다 |

### `data` 안의 항목

| 이름 | 뜻 | 값 |
|---|---|---|
| `b_no` | 사업자등록번호 | 보낸 값 그대로 |
| **`b_stt_cd`** | **납세자 상태 코드** ← 곳간이 판정에 쓰는 값 | `01` 계속사업자 / `02` 휴업자 / `03` 폐업자 / **빈 문자열 = 미등록** |
| `b_stt` | 납세자 상태 이름 | `계속사업자` / `휴업자` / `폐업자` / 빈 문자열 |
| `tax_type_cd` | 과세유형 코드 | `01` 일반과세자 / `02` 간이과세자 / `03` 과세특례자 / `04` 면세사업자 / `05` 비영리법인·국가기관 등 / `06` 고유번호 단체 / `07` 간이과세자(세금계산서 발급) |
| `tax_type` | 과세유형 이름 | 미등록이면 여기에 **"국세청에 등록되지 않은 사업자등록번호입니다."** 문장이 들어온다 |
| `end_dt` | 폐업일 | `YYYYMMDD`. 폐업자일 때만 값이 있다 |
| `utcc_yn` | 단위과세 전환 폐업 여부 | `Y` / `N` |
| `tax_type_change_dt` | 최근 과세유형 전환일 | `YYYYMMDD` 또는 빈 문자열 |
| `invoice_apply_dt` | 세금계산서 적용일 | `YYYYMMDD` 또는 빈 문자열 |
| `rbf_tax_type_cd` | 직전 과세유형 코드 | `01` / `02` / `07` / `99` 해당없음 |
| `rbf_tax_type` | 직전 과세유형 이름 | |

**값이 없으면 `null`이 아니라 빈 문자열 `""`이 온다.**

### 폐업자 예시 (공식 명세 기준, 실제 호출 아님)

```json
{
    "b_no": "0000000000",
    "b_stt": "폐업자",
    "b_stt_cd": "03",
    "tax_type": "부가가치세 일반과세자",
    "tax_type_cd": "01",
    "end_dt": "20000101",
    "utcc_yn": "N",
    ...
}
```

## 4. 응답 — 경우별 실제 결과

### 4-1. `b_no`가 빈 배열이거나 아예 없을 때

```
요청 본문: {"b_no":[]}  또는  {"foo":"bar"}
HTTP 411
{"status_code": "REQUEST_DATA_MALFORMED"}
```

### 4-2. 101개 이상 보냈을 때

```
HTTP 413
{"status_code": "TOO_LARGE_REQUEST"}
```

### 4-3. 하이픈을 넣었을 때 ⚠

```
요청 본문: {"b_no":["108-86-12463"]}      ← 실제로는 영업 중인 번호
HTTP 200
{
    "request_cnt": 1,                     ← match_cnt 가 없다
    "status_code": "OK",
    "data": [{
        "b_no": "108-86-12463",
        "b_stt": "", "b_stt_cd": "",
        "tax_type": "국세청에 등록되지 않은 사업자등록번호입니다.",
        ...
    }]
}
```

**오류가 아니라 200 + "미등록"으로 온다.** 그래서 곳간은 보내기 전에 반드시 `BizNumber::normalize()`로 숫자만 남긴다.

## 5. 오류 응답 정리

| HTTP | 본문 | 언제 | 확인 |
|---|---|---|---|
| 401 | `{"code": -4, "msg": "등록되지 않은 인증키 입니다."}` | 키가 틀렸거나, 변환된 키를 한 번 더 변환해서 보냄 | 실제 호출 |
| 411 | `{"status_code": "REQUEST_DATA_MALFORMED"}` | `b_no`가 비었거나 없음 | 실제 호출 |
| 413 | `{"status_code": "TOO_LARGE_REQUEST"}` | 100개 초과 | 실제 호출 |
| 400 | `status_code` 포함 | JSON 형식이 깨짐 | 명세 |
| 404 | | 주소가 틀림 | 명세 |
| 500 | `status_code` 포함 | 국세청 쪽 내부 오류 | 명세 |

오류 본문의 모양이 두 가지다. 인증 오류는 `code`/`msg`, 나머지는 `status_code`. **HTTP 상태 코드로 먼저 가르는 것이 안전하다.**

## 6. 곳간 코드에서는

### 부르는 곳

| 언제 | 위치 |
|---|---|
| 가입 신청 | `resources/views/components/auth/⚡register.blade.php:136` — 계속사업자가 아니면 가입을 막는다 |
| 존속 점검 (관리자가 수동 실행) | `app/Console/Commands/BusinessCheck.php:37` — 결과를 `existence_checks`에 남긴다 |

둘 다 `App\Support\BiznoStatus::check($번호)` 하나를 부른다. 실제 호출은 `BiznoStatus.php:39`의 `checkViaNts()`에 있다.

### 흐름

```
BiznoStatus::check('108-86-12463')
  ├─ BizNumber::normalize() → '1088612463'      숫자만 남긴다 (4-3 때문에)
  ├─ BIZNO_DRIVER=log  → 국세청을 부르지 않고 형식만 검사 (개발용)
  └─ BIZNO_DRIVER=nts  → checkViaNts()
        ├─ 키가 비었으면 → error
        ├─ 키에 % 가 있으면 urldecode (포털 키를 그대로 넣어도 되게)
        ├─ POST /status?serviceKey=…  본문 {"b_no":["1088612463"]}  (10초 제한)
        ├─ 통신 실패 / HTTP 200 이 아님 → error  (오류 문구에서 키는 *** 로 가림)
        └─ data[0].b_stt_cd 로 판정
```

### 판정표

| 국세청 `b_stt_cd` | `BiznoStatus` 결과 | 가입 화면 | `existence_checks.result` |
|---|---|---|---|
| `01` | `active` | 통과 | 1 계속사업자 |
| `02` | `suspended` | "휴업 사업자로 조회됩니다. 가입할 수 없습니다." | 3 휴업 |
| `03` | `closed` | "폐업 사업자로 조회됩니다. 가입할 수 없습니다." | 2 폐업 |
| `""` (빈 값) | `not_found` | "국세청에서 조회되지 않는 번호입니다." | 4 미등록 |
| 그 밖의 값 / 통신 실패 / HTTP 오류 | `error` | "사업자 상태를 조회하지 못했습니다. 잠시 후 다시 시도해 주세요." | 0 조회 실패 |

**조회 실패는 폐업이 아니다.** 키 누락·통신 오류는 "조회 실패(0)"로 따로 남기고, 회원 상태나 매물은 건드리지 않는다.

### 곳간이 저장하는 것

| 저장 | 저장 안 함 |
|---|---|
| `b_stt_cd` (`existence_checks.raw_status_code`), 판정 결과, 조회 시각 | `tax_type`, `end_dt` 등 나머지 항목. 사업자번호도 `existence_checks`에는 넣지 않는다(회원 번호로 연결) |

폐업일(`end_dt`)을 관리자 화면에 보여 주고 싶어지면 `checkViaNts()`의 반환값에 더하면 된다.

### 한 명씩 부른다

API는 한 번에 100개까지 받지만 `BusinessCheck`는 회원마다 한 번씩 부른다. 회원이 수천 명이 되면 100개씩 묶어 부르도록 바꾼다(`BusinessCheck.php`에 `ponytail:` 주석).

## 7. 직접 호출해 보기

### curl

포털 키를 그대로 붙인다.

```bash
curl -X POST "https://api.odcloud.kr/api/nts-businessman/v1/status?serviceKey=포털_일반인증키" \
     -H "Content-Type: application/json" \
     -d '{"b_no":["1088612463"]}'
```

### 곳간 코드로

`.env`가 `BIZNO_DRIVER=nts`일 때:

```bash
docker exec gotgan-laravel.test-1 php artisan tinker --execute="print_r(App\Support\BiznoStatus::check('108-86-12463'));"
```

```
Array
(
    [result] => active
    [code] => 01
    [error] =>
)
```

### 존속 점검 명령

```bash
docker exec gotgan-laravel.test-1 php artisan app:business-check --limit=3
```

결과는 관리자 → 존속 점검(`/admin/existence-checks`)에서 본다.

## 8. 설정

| `.env` | 값 | 뜻 |
|---|---|---|
| `BIZNO_DRIVER` | `log` | 국세청을 부르지 않는다. 형식 검사만 하고 맞으면 계속사업자로 본다(개발용) |
| | `nts` | 실제 국세청 조회 |
| `BIZNO_API_KEY` | 포털 '일반 인증키' | 그대로 붙여 넣는다 |

테스트는 `.env`와 상관없이 항상 `log`로 돈다(`phpunit.xml`). 국세청 호출 테스트(`tests/Feature/BusinessCheckTest.php`)는 `Http::fake()`로 가짜 응답을 쓴다.
